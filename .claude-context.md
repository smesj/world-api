# World API - Claude Context

## Project Overview

**World API** is a unified NestJS backend that consolidates all smesj ecosystem applications into a single modular monolith. This architecture replaces separate microservices with domain-specific modules while maintaining clear boundaries and separation of concerns.

- **Repository**: world-api
- **Domain**: world-api.smesj.world
- **Port**: 3003
- **Database**: Single PostgreSQL database with logical domain separation
- **Architecture**: Modular monolith with five main modules (Identity, Footy, Imperial, Toshi Ranbo, Webhooks)

## Architecture Decision

This project was created to replace a microservices architecture with a modular monolith based on:

- Solo developer context (just smesj)
- Small scale operation (friends/family)
- 100% user overlap across all apps
- Tightly related domains
- Need for fast iteration
- Benefits: shared transactions, type safety, simpler operations
- Can split into microservices later if needed

### 4. Toshi Ranbo Module (`src/modules/toshi-ranbo`)

**Purpose**: Toshi Ranbo (board game) result recording and player roster

**Status**: Implemented

**Components**:
- `games.controller.ts` / `games.service.ts` - Record a completed game and its player results in one call
- `players.controller.ts` / `players.service.ts` - Manage the guest player roster
- `dto/games.dto.ts`, `dto/players.dto.ts` - DTOs for request validation

**Key Features**:
- No Clerk signup required to be a "player" — players are a lightweight
  name-only roster (`ToshiRanboPlayer`), decoupled from the Clerk-backed
  `User` model, created on demand via the API
- Records a whole game (cards played + every player's clan, total
  points, and which of 10 fixed point categories they scored) in a
  single write, validating all player IDs up front
- Reuses the shared `Game` table as the aggregate root (like Footy),
  with `ToshiRanboGame` holding game-level stats and `ToshiRanboScore`
  holding one row per player per game
- Optional board photo per game, uploaded separately after game
  creation and stored in Cloudflare R2 (see "Board Photos" below)

**API Endpoints** (🔒 = requires `X-Api-Key` header, see Authentication below):
```
POST   /toshi-ranbo/players       🔒 - Create a guest player (409 on duplicate name)
GET    /toshi-ranbo/players       - List all guest players
POST   /toshi-ranbo/games         🔒 - Record a completed game + all player results
GET    /toshi-ranbo/games/:id     - Get game details
POST   /toshi-ranbo/games/:id/photo 🔒 - Upload/replace the board photo (multipart, field "photo")
DELETE /toshi-ranbo/games/:id     🔒 - Delete a game (e.g. mis-recorded or test entry); cascades to its scores, but does NOT delete the photo object from R2
```

**Database Models**:
- `ToshiRanboPlayer` - Guest player roster (name-only, no Clerk account)
- `ToshiRanboGame` - Game-level stats (1:1 with `Game`), e.g. cards played, `photoUrl`
- `ToshiRanboScore` - Player scores per game, including 11 boolean point-category flags

#### Board Photos

Games can optionally have a photo of the board attached after
creation via `POST /toshi-ranbo/games/:id/photo` (multipart
form-data, field name `photo`; JPEG/PNG/WEBP/GIF, max 10MB). The
image is uploaded to a Cloudflare R2 bucket by `R2StorageService`
(`src/shared/r2-storage.service.ts`) and the resulting public URL is
saved to `ToshiRanboGame.photoUrl`. Re-uploading replaces the URL
(the old object is not deleted from R2).

Requires `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`,
`R2_BUCKET_NAME`, and `R2_PUBLIC_URL` to be set (see
`.env.production.example`) — without them the endpoint returns 503.
Not configured in local dev by default.

If smesj shares a photo of the board alongside game results, upload
it as a follow-up step after `POST /toshi-ranbo/games` succeeds:
`POST /toshi-ranbo/games/:id/photo` with the image as multipart field
`photo`, using the `id` from the just-created game.

**Seed Data**: The initial roster (Smesj, Cam, Moose, Alan, Babin, Ted,
Ginny) is pre-populated by migration
`prisma/migrations/20260911172352_seed_toshi_ranbo_players`, using
`INSERT ... ON CONFLICT ("name") DO NOTHING` so it's safe even if ever
re-run outside Prisma's own once-per-migration tracking.

#### Recording Game Results (Workflow)

smesj pastes game results from game night in shorthand, one game per
block, looking like:

```
Game 3 (4 card)
Alan - Crab - 3 (2b-1c-2c)
Cam - Lion - 3 (f1-3c-2b)
Moose - Crane - 7 (tr-f1-3t-1t-3o-2b-c1)
Smesj - Unicorn - 0
```

First line = cards played. Each following line = `Player - Clan -
TotalPoints (shorthand codes)`.

**Shorthand → category mapping** (codes are casually reordered/typo'd
by hand — treat digit+letter and letter+digit as the same category,
e.g. `1f` and `f1` both mean the same thing):

| Codes seen | Category (`ToshiRanboScore` column) |
|---|---|
| `1f`, `f1` | `fightWin1f` — First Fight Win |
| `2f`, `f2` | `fightWin2f` — Second Fight Win |
| `3v`, `3c` (was confirmed to mean "3 villages", not "3 cities") | `threeVillages` |
| `1t` | `firstToshiRanbo` — permanent point for first to Toshi Ranbo |
| `tr` | `heldToshiRanbo` — separate **transient** point for holding it, stacks with `1t` |
| `2s`, `2sh` | `twoShrines` |
| `3n`, `3o` (typo, o/n adjacent keys) | `threeNobleActions` |
| `2b` | `twoBuildings` |
| `3t` | `threeTactics` |
| `c1`, `1c` | `clanGoal1` — First Clan Goal |
| `c2`, `2c` | `clanGoal2` — Second Clan Goal |

`heldToshiRanbo` was discovered mid-recording (Sep 2026) as a real,
previously-untracked category — if a future shorthand code doesn't
match anything above and isn't an obvious typo of one, **ask** rather
than guessing; it may be a genuine 12th category needing a new
migration (see `add_held_toshi_ranbo` for the precedent: add the
column, migrate locally, commit, deploy, *then* record the game).

**Process**:
1. Decode every line using the table above. Flag anything ambiguous
   or unrecognized and ask for clarification — don't guess silently.
2. **Repeat the full decoded interpretation back to smesj for
   confirmation before writing anything.**
3. Look up player IDs: `GET /toshi-ranbo/players` (returns
   `{id, name}[]`). Players are matched by name, not passed as names —
   the API takes numeric `playerId`.
4. Submit the whole game in one call:
   `POST /toshi-ranbo/games` with body
   `{ cardsPlayed, results: [{ playerId, clan, totalPoints, ...booleanFlags }] }`
   (see `dto/games.dto.ts`). `totalPoints` is trusted input — it is
   **not** derived from the flags server-side (clan goals don't have a
   fixed point value, so summing flags isn't reliable). **Requires an
   `X-Api-Key` header** (see Authentication below) — this and every other
   mutating toshi-ranbo call (`POST .../photo`, `DELETE .../:id`,
   `POST /toshi-ranbo/players`) are guarded; only the `GET`s are open.
5. Verify with `GET /toshi-ranbo/games/:id` on the response, or
   `GET /toshi-ranbo/games` to see it in the full list.
6. Prod API base: `https://world-api.smesj.world`. Local dev:
   `http://localhost:3003` — **player IDs differ between the two**
   (local dev DB has drifted IDs from early test data), always look
   them up fresh per-environment rather than reusing numbers.

### 5. Webhooks Module (`src/modules/webhooks`)

### 6. Toshi Telegram Bot Module (`src/modules/toshi-telegram-bot`)

**Purpose**: Lets game night members run `/game`, then reply to the bot's
prompt with the board photo + shorthand scores in its caption; Claude
decodes it into the same structured shape the manual recording workflow
produces, a human confirms in-chat, and it's saved via the Toshi Ranbo
module.

**Trigger flow note**: the supported flow is **`/game`, then reply to that
prompt with the photo**. This went through several wrong theories during
Sep 2026 testing before landing here — worth recording so it isn't
re-litigated:
- ❌ A single message with the photo + a caption containing `@ToshiGameBot`
  — never delivered. Group privacy mode does **not** have an "explicit
  @mention" exception (this was assumed, incorrectly, twice).
- ❌ Post the photo untagged, then reply to it with plain text containing
  `@ToshiGameBot` — also never delivered. Replying to a message from a
  regular *user* doesn't qualify for any privacy-mode exception, no matter
  what the reply says.
- ✅ **Confirmed by direct testing**: privacy mode's only two delivery
  exceptions are (1) commands, and (2) replies to a message **from the bot
  itself**. Everything here is built on those two, nothing else — no
  @mention detection anywhere in the code.
- `/game` posts a prompt message; replying to it (photo attached, scores in
  the caption) is a reply to the bot's own message, so delivery is
  guaranteed. `handleGameMessage` additionally checks `isReplyToBot()`
  itself rather than assuming Telegram only ever forwards intended
  messages — belt and suspenders, and future-proofs against privacy mode
  ever being toggled off.
- `handleTextMessage` only fires for a reply-to-bot with no photo attached
  (nudges the poster to attach one) — a reply *with* a photo is a
  `message:photo` update and goes straight to `handleGameMessage`.

**Status**: Implemented

**Naming note**: named `toshi-telegram-bot`, not just `telegram-bot` — if a
Telegram bot is ever built for a different game/domain, it gets its own
sibling module (`<domain>-telegram-bot`) instead of overloading this one.

**Components**:
- `toshi-telegram-bot.service.ts` - Owns the grammy `Bot` instance (long polling,
  not a webhook — no extra Cloudflare tunnel route needed), message/callback
  handlers, lifecycle (`onModuleInit`/`onModuleDestroy`)
- `game-interpreter.service.ts` - Single Claude API call (`messages.parse` +
  a Zod output schema) that decodes a caption into structured data; never
  touches the database
- `pending-confirmation.store.ts` - In-memory `Map` holding a decoded game
  (plus the downloaded photo buffer) between the bot's confirmation prompt
  and the Confirm/Cancel button tap; entries expire after 15 minutes
- `shorthand-table.ts` - The same shorthand → category table documented
  below in "Recording Game Results", duplicated here as the system-prompt
  text for the Claude call. **Keep both in sync by hand.**

**Key Features**:
- No HTTP surface of its own — imports `ToshiRanboModule` and calls
  `GamesService`/`PlayersService` directly in-process (no new REST hop)
- Relies on Telegram's **group privacy mode** (on by default; the bot must
  stay a non-admin member — admin rights disable privacy mode entirely) so
  only `/commands` and replies to the bot's own messages are ever delivered
  to it — ordinary chat between members in the same group never reaches the
  bot or triggers an LLM call
- `/chatid` command (works in any chat, privacy mode always allows commands
  through) — used once during setup to find the value for
  `TELEGRAM_ALLOWED_CHAT_ID`
- Defense-in-depth chat allow-list: `TELEGRAM_ALLOWED_CHAT_ID` — if unset,
  the bot logs a startup warning and will act in any chat it's added to
- Decode step never guesses: unrecognized shorthand codes or player names
  that don't match the live roster (`PlayersService.findAll()`, matched
  case-insensitively) block confirmation and ask the poster to clarify,
  rather than creating a new player or picking a category — same rule as
  the manual workflow
- Photo is downloaded once at decode time (`ctx.api.getFile` +
  `https://api.telegram.org/file/bot<token>/<file_path>`) and held with the
  pending entry, rather than re-fetched at confirm time, since Telegram's
  file links expire
- On confirm: `GamesService.createGame(...)` then
  `GamesService.setGamePhoto(...)` (built from the buffer, no multipart HTTP
  round-trip), same in-process services the manual `POST /toshi-ranbo/games`
  and `.../photo` endpoints use
- Confirmation prompt and result are posted back into the group (not DMed)
  so all members see and can dispute a recorded game

**Configuration** (all unset in local dev → bot logs a warning and skips
starting; see `.env.production.example`):
- `TELEGRAM_BOT_TOKEN` - from `@BotFather`
- `TELEGRAM_ALLOWED_CHAT_ID` - the one group chat it's allowed to act in
- `ANTHROPIC_API_KEY` - **dedicated key for this bot**, with a Console
  spend cap set — game-night volume costs pennies/month, so the cap is a
  safety net against something being broken (spam, a retry loop), not a
  real usage limit
- `ANTHROPIC_MODEL` - defaults to `claude-sonnet-5` if unset

## Shared Infrastructure

### PrismaService (`src/shared/prisma.service.ts`)

Shared Prisma client used across all modules:
- Connects on module initialization
- Provides unified database access
- Handles graceful shutdown

### Database Schema (`prisma/schema.prisma`)

Single unified schema with logical domain separation:

**Identity Domain**:
- `User` - Central user model (Clerk ID as primary key)
- `Invitation` - Invitation code management

**Footy Domain**:
- `FootyGame` - Table football game records

**Imperial Domain**:
- `ImperialGame` - Imperial game sessions
- `ImperialScore` - Player scores per game

**Toshi Ranbo Domain**:
- `ToshiRanboPlayer` - Guest player roster, independent of `User`/Clerk
- `ToshiRanboGame` - Game-level stats (1:1 with the shared `Game` table)
- `ToshiRanboScore` - Player scores per game

Identity, Footy, and Imperial models connect through the central `User`
model for consistent user references. Toshi Ranbo is the exception —
its players are intentionally decoupled from `User` so games can be
recorded without anyone signing up first (see Toshi Ranbo Module above).

### Database Management

**Migration Workflow** (Important - Follow This Process):

Due to non-interactive shell limitations in Claude Code, migrations must be run manually:

1. Claude modifies `schema.prisma` with new/updated models
2. User runs: `npx prisma migrate dev --name <description>`
3. Claude verifies migration success with database queries if needed

This creates proper migration files in `prisma/migrations/` and applies them to the database.

**Other Database Commands**:
```bash
# Apply production migrations
npx prisma migrate deploy

# View database in Prisma Studio
npx prisma studio

# Reset database (dev only)
npx prisma migrate reset
```

**Note**: Never use `npx prisma db push` for migrations. It skips creating migration files which breaks production deployments.

## API Conventions

### Response Formats

**Success**:
```json
{
  "id": "uuid",
  "field": "value",
  ...
}
```

**Error**:
```json
{
  "statusCode": 400,
  "message": "Error description",
  "error": "Bad Request"
}
```

### Validation

All endpoints use DTOs with class-validator decorators:
- `@IsString()`, `@IsInt()`, `@IsOptional()`, etc.
- Automatic validation via global ValidationPipe
- Whitelist mode (strip unknown properties)
- Transform mode (convert types)

### Authentication

No real authentication middleware is implemented — user IDs are passed in
request bodies, and CORS is wide open (`origin: '*'`). Full Clerk JWT auth
(validate JWT, extract user ID, inject user context, guard endpoints) is
still the eventual real fix and remains undone.

One narrow gap has a stopgap, added Sep 2026 after standing up the Toshi
Telegram bot made it obvious anyone finding `world-api.smesj.world` could
freely mutate game data: `src/shared/api-key.guard.ts` (`ApiKeyGuard`) is a
shared-secret check — `X-Api-Key` header against the `ADMIN_API_KEY` env
var, fails closed if unset — applied via `@UseGuards(ApiKeyGuard)` to
toshi-ranbo's mutating routes only (`POST`/`DELETE` on games, `POST` on
players; `GET`s stay open since the public dashboard depends on them).
Deliberately not real auth — no per-user identity, one shared secret — but
proportionate to a friends-and-family hobby project, and cheap to extend:
Imperial and Footy have the exact same open-mutation gap and aren't guarded
yet. The Telegram bot is unaffected either way — it calls
`GamesService`/`PlayersService` directly in-process, never over HTTP, so a
controller-layer guard doesn't touch it.
